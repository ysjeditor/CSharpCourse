# TIL 실습 — 경험을 남이 사용할 설명으로 바꾸기

## 목표·준비

증상이 드러나는 제목을 만들고 상황·입력·실패 가설·해결·검증·한계를 연결한다. 강사는 작은 실제 문제, 시도 로그, 전후 커밋, 좋은 글/일기형 글의 비교와 완성본을 준비한다. 실패한 시도나 측정값을 글을 채우려고 꾸며내지 않는다.

## 준비 → 첫 글 → 타인 재현 → 독립 글

1. 문제1개를 골라 독자를 정한다. ‘미래의 나’도 당시 맥락을 모르는 독자로 가정한다.
2. 강사①: 로그·코드를 보여주며 문제→가설→시도→관찰→수정→검증을 백지에서 작성한다. 처음 제목을 구체적 증상 중심으로 고치는 과정을 보인다.
3. 학생②: 같은 문제의 글을 작성하고 독자가 바로 확인할 입력·조건을 적는다.
4. 사고 시간을 두고 자기 프로젝트의 다른 조건을 골라 새 가설을 세우거나 적용 한계를 검토한다. 해결책부터 복사하지 않는다.
5. 독자가 글만 보고 재현 또는 적용하고 막힌 문장을 질문한다. 작성자는 설명을 보완한다.
6. 코드·증거·글을 PR로 제출하고 받은 질문·응답·수정을 연결한다.

## ② 판단 빈칸5개

```markdown
# 증상과 해결 행동이 보이는 제목: ____
  [힌트: ‘오늘 배운 것’ 대신 언제 무엇이 잘못됐는가]
- 상황·환경·입력·문제: ____
  [힌트: 독자가 같은 출발점을 만들 수 있게]
- 가설·시도·관찰 결과: ____
  [힌트: 실패도 포함하되 실제 수행한 내용만]
- 해결·원인·검증 증거: ____
  [힌트: 무엇을 바꿨고 같은 조건에서 무엇이 달라졌나]
- 교훈·적용 한계·다음 확인: ____
  [힌트: 다음 사람이 취할 행동으로]
```

## ③ 서술형 — 트러블슈팅 개발기

800~1500자를 예시 분량으로 두고 코드·로그는 링크하거나 필요한 부분만 포함한다.

- 어떤 상황에서 무엇이 잘못됐고, 독자는 어떻게 확인할 수 있는가?
  ⤷ 더 강한 답: 발생/비발생 조건의 차이까지 설명한다.
- 어떤 가설을 세워 시도했고 왜 맞거나 틀렸는가?
  ⤷ 더 강한 답: 실패를 다음 선택의 근거로 연결한다.
- 원인을 어떻게 확인했고 해결의 한계는 무엇인가?
  ⤷ 더 강한 답: 같은 해결이 통하지 않는 반례를 제시한다.

## ④ 자유형 과제

목적: 스스로 겪은 문제를 낯선 독자가 재현·해결·응용할 수 있는 기술 글로 설명한다.

공통 루브릭: 목적 적합·구조·근거·재현/적용·회고.

흔한 실패: 일기/작업 목록, 결과만 설명, 검색 글 복사, 해결하지 않았는데 해결한 것으로 표기.

## 제출·리뷰·완료

글+관련 코드/증거+PR을 제출한다. 리뷰는 제목의 예측 가능성, 실패 가설의 근거, 독자의 재현 가능성을 확인한다. 예: `[question] 해결 절 — 바꾼 뒤 어떤 입력으로 다시 확인했나요? 이전과 같은 조건의 결과를 연결해 주세요.`

완료: 동료가 문제·해결·적용 한계를 자기 말로 설명하고 관련 증거를 찾을 수 있다. 다음 과제는 다른 증상 또는 이전 글의 미확인 부분을 검증해 연결 글로 확장한다. 공개 블로그 발행은 별도 수업 운영 선택이며 원격 게시 없이도 저장소 글을 결과물로 인정한다.
