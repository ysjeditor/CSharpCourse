02 · 코드 섹션 책임

한 바퀴(while (running) { … }) 안의 4개 섹션이 각각 어떤 변수를 읽고 쓰는지:

섹션줄 범위책임읽는 변수쓰는 변수
Render17~22화면 출력gold·grade·bestGrade·cost·chance·sellPrice·message—
종료 조건 검사25~34승리/파산 판정 후 breakgrade·gold·bestGrade—(break만)
Input37~38메뉴 입력 받기—choice
Update41~83choice에 따라 조건문으로 분기choice·gold·cost·chance·sellPrice·gradegold·grade·bestGrade·message·running

Render는 아무 상태도 바꾸지 않는다(읽기 전용) — 화면은 "지금 상태를 보여줄 뿐"이고, 상태를 바꾸는 건 항상 Update라는 것이 이 구조의 핵심이다.

03 · while 코드 대응 — 게임기획과 줄 번호

게임기획.html 03장의 반복 흐름은 Program.cs의 구조와 한 줄씩 대응된다. 실습할 때는 아래 순서로 코드를 따라가며 게임기획 문서를 옆에 놓고 비교한다.

게임기획 문서코드 위치확인할 것
반복 조건(변수)bool running = true;(6행) → while (running)(10행)"몇 번"이 아니라 조건이 거짓이 될 때까지 도는 구조 — for가 아닌 이유
① Render// Render: 주석(16행) 아래 Console.Clear()~Console.WriteLine(message)(17~22행)게임기획 02장 6줄이 코드 6줄과 1:1로 대응하는지 확인
② 종료 조건if (grade >= 10) { … break; }(25~29행) / if (gold < 10 && grade == 0) { … break; }(30~34행)반복 안에서 break로 빠져나가는 것과 running = false로 다음 바퀴 조건에서 빠져나가는 것의 차이
③ Input// Input: 주석(36행), Console.ReadLine()(38행)한 바퀴 = 한 번의 입력(턴 방식)
④ Update// Update: 주석(40행), if (choice == "1") … else if (choice == "2") … else if (choice == "0" …) … else …(41~83행)조건문 분기 4가지가 게임기획 03장의 강화/팔기/종료/잘못된 입력과 정확히 대응

04 · 실습 과제 (코드를 고치며 확인)

  1. bestGrade를 출력하는 줄(19행)을 지워 보고, 왜 "최고 기록"이 게임기획 02장 표에서 "탈락하지 않은 정보"였는지 다시 설명해 본다.
  2. 파산 조건(30행)을 gold < 10으로만(등급 조건 삭제) 바꿔 보고, 등급을 올린 상태에서도 파산이 되는 버그가 생기는 것을 확인한다 — 종료 조건은 화면에 보이는 값과 일치해야 한다는 걸 체감하는 과제.
  3. while (running)(10행)을 for (int i = 0; i < 5; i++)로 바꿔보고 왜 이 게임에 for가 맞지 않는지 말로 설명한다(턴 수를 미리 알 수 없음).
