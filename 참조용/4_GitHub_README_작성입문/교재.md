# GitHub README 작성 입문

## 01. 코드와 문서를 어디에 두나요?

### 시작점은 저장소 루트입니다

`templates/1_Project`를 복사해 자신의 저장소 루트로 사용한다고 가정합니다. GitHub의 첫 화면에 표시하는 주 README는 루트의 **README.md**입니다. assets와 src 안의 README는 다른 파일입니다. 대소문자 문제를 줄이려면 실제 이름도 `README.md`로 통일하세요.

<!-- FOLDERS -->

### 폴더마다 맡는 일

| 위치 | 넣을 것 | README에 연결할 방법 |
| --- | --- | --- |
| 루트 README.md | 주제·오늘 기록 요약·바로가기·실행 방법 | 방문자가 처음 읽는 안내 |
| assets | 실행 화면·그림·GIF | 이미지 문법으로 표시 |
| docs | 개발 일지·TIL·설명·어려웠던 점 | 링크로 상세 내용 연결 |
| src | 실제 소스와 프로젝트 파일 | 소스 링크와 실행 명령 연결 |

README에 긴 개발 과정을 모두 넣기보다 **무엇을 했는지 요약하고 상세 문서로 안내**합니다. 새로 구현한 사실이 없다면 구현 완료라고 적지 않고 ‘개념 정리’나 ‘실험 중’처럼 현재 상태를 적습니다.

### 먼저 만들 파일

이 가이드는 고정 예시 날짜 2026-11-19를 사용합니다. 실제 작성할 때는 자신의 날짜·주제·프로젝트 이름으로 바꿉니다. 예시 문서는 `docs/2026-11-19-콘솔출력/`, 실제 코드는 `src/HelloReadme/`에 둡니다. 원본 템플릿을 수정하는 대신 별도 실습 저장소에서 작업하세요.

## 02. Markdown 기호와 결과를 연결하기

### 파일은 글이고 기호가 서식입니다

Markdown은 텍스트에 제목·목록·링크 같은 의미를 표시하는 문법입니다. `.md` 파일에 적은 원문과 GitHub가 보여주는 결과를 구분합니다. 코드의 `#`와 달리 Markdown 문서 첫머리의 `#`는 제목 기호가 될 수 있습니다.

아래 버튼을 고르면 **입력할 원문과 표시 결과**를 함께 볼 수 있습니다. 이 미리보기는 학습할 기본 문법을 보여주는 것이며 GitHub의 모든 확장 문법을 재현하는 편집기는 아닙니다.

<!-- SYNTAX -->

### 자주 쓰는 기호

- 제목은 `# 제목`, 큰 구역은 `## 개발 기록`처럼 씁니다. 기호 뒤에 공백을 둡니다.
- 강조는 `**중요한 말**`, 짧은 코드 이름은 백틱 하나씩으로 감쌉니다.
- 링크는 `[보이는 글자](이동할 경로)`, 이미지는 앞에 느낌표가 붙은 `![설명](이미지 경로)`입니다.
- 여러 줄 코드와 명령은 백틱 세 개로 열고 닫습니다. 시작 뒤에 csharp나 bash 같은 언어 이름을 쓸 수 있습니다.
- 표는 `|`로 열을 나누고 둘째 줄에 `---` 구분선을 둡니다.

제목·문단·목록·표 앞뒤에 빈 줄을 넣으면 구조를 구별하기 쉽습니다. 코드 블록에 넣은 Markdown 기호는 제목으로 바뀌지 않고 그대로 표시됩니다. 초보자가 자주 놓치는 것은 **열고 닫는 백틱의 개수**, 링크 괄호, 이미지 앞의 느낌표입니다.

## 03. README의 정확한 수정 위치 찾기

### 버튼으로 원본과 수정 결과를 대조하세요

왼쪽은 `templates/1_Project/README.md`의 원본 또는 완성 예시 원문이고, 오른쪽은 서식이 적용된 결과입니다. 작업 버튼을 누르면 **수정 대상 줄이 자동으로 보이는 위치로 이동하고 강조**됩니다. 번호는 현재 예시에 대한 보조 정보이며 실제 저장소에서는 제목과 표 구분선을 기준으로 찾습니다.

<!-- README_MAP -->

### 교체·추가·유지를 구별하기

프로젝트 제목과 설명은 기존 안내 문구를 교체합니다. 개발 기록은 표의 구분선 바로 아래에 **새 행을 삽입**하여 최신 날짜가 위로 오게 합니다. 기존 날짜 행은 지우지 않습니다. 실행 화면은 새 구역으로 추가하고, 실행 명령은 실제 csproj 위치에 맞게 바꿉니다.

오른쪽 미리보기의 강조 구역은 작업할 구역을 알려줍니다. 이미지나 상세 문서 링크를 눌러 서버에 업로드하는 기능은 아닙니다. 이 가이드가 GitHub 저장소를 자동으로 수정하지 않으므로, 자신의 README에 선택한 문장을 반영해야 합니다.

## 04. 하루 기록은 세 군데를 연결합니다

### 상세 문서 → 날짜 인덱스 → README 요약

먼저 `docs/2026-11-19-콘솔출력/TIL.md`에 무엇을 배웠는지 적습니다. 구현했다면 설명.md에 파일 역할과 입력·결과를 남깁니다. 다음 `docs/개발일지.md`의 최신 날짜 구역에 해당 문서 링크를 추가하고, 마지막으로 루트 README의 개발 기록 표에 요약 한 행을 추가합니다.

| 단계 | 정확한 위치 | 적을 내용 |
| --- | --- | --- |
| 상세 작성 | docs의 날짜·주제 폴더 | 규칙·시도·코드·실행 결과 |
| 날짜 인덱스 갱신 | docs/개발일지.md의 최신 날짜 위치 | 한 일·작성 문서·막힌 점·다음 일 |
| 요약 갱신 | 루트 README 개발 기록 표 구분선 아래 | 날짜·짧은 한 일·문서 링크·PR 상태 |

### 새 행을 넣는 위치

개발 기록 표의 제목 줄과 `| --- | ... |` 구분선은 그대로 둡니다. 그 바로 다음에 오늘 행을 넣고, 어제 행은 그 아래에 둡니다. 표 한 행 안에서 임의로 줄바꿈하지 않습니다. 내용에 세로줄을 문자로 쓰려면 역슬래시로 이스케이프합니다.

PR을 아직 만들지 않았다면 `작성 전`이라고 적습니다. 원본의 `[PR](____)` 같은 자리표시자를 실제로 동작하는 링크처럼 남기지 마세요. PR을 연 다음 자신의 실제 주소를 복사하여 해당 칸만 갱신합니다.

### 파일의 역할이 다른 이유

README는 요약 허브, 개발 일지는 날짜별 상세 기록의 인덱스, 주제 문서는 실제 학습 내용입니다. 같은 긴 글을 세 군데 복제하지 않고 링크로 연결하면 수정할 곳과 찾을 곳이 분명해집니다.

## 05. 이미지와 문서의 상대경로

### 경로의 출발점은 링크를 적는 문서입니다

`./`는 현재 문서가 있는 폴더, `../`는 한 단계 위 폴더입니다. 상대경로는 실행할 때의 터미널 폴더나 VS Code 작업 폴더가 아니라 **그 Markdown 파일의 위치**를 기준으로 해석합니다.

<!-- PATHS -->

### 같은 이미지도 문서 위치에 따라 달라집니다

루트 README에서 assets로 가면 `./assets/console-output.svg`입니다. docs/개발일지.md에서는 한 번 올라가 `../assets/console-output.svg`이고, 날짜·주제 하위의 설명.md에서는 두 번 올라가 `../../assets/console-output.svg`가 됩니다.

assets/README의 ‘docs 안에서는 ../assets’ 예시는 **docs 바로 아래 문서 기준**입니다. docs 아래에 폴더가 더 있으면 그대로 복사하지 말고 출발 위치부터 다시 계산해야 합니다.

### GitHub에 올려도 유지되는 경로

Windows의 `C:\...` 같은 개인 PC 경로를 GitHub 문서에 넣지 않습니다. 저장소 파일 링크에는 `/`를 사용하고 이름·대소문자·확장자를 실제 파일과 맞춥니다. 한글 이름도 사용할 수 있지만 정확하게 링크해야 합니다. URL에 민감한 공백·괄호가 있는 경우 인코딩하거나 파일 이름을 단순하게 정리합니다. 이 실습의 이미지 파일명은 영문과 하이픈으로 고정했습니다.

## 06. 실행 방법은 실제 프로젝트 위치에 맞추기

### src 폴더와 csproj 파일은 같지 않습니다

원본 src/README의 `dotnet new console -n 프로젝트이름`을 src에서 실행하면 그 아래에 프로젝트 폴더가 생깁니다. src 바로 아래에 csproj가 없는데 README에 단순히 `cd src`와 `dotnet run`만 적으면 실행 대상을 못 찾을 수 있습니다.

이 실습의 실제 파일은 `src/HelloReadme/HelloReadme.csproj`입니다. **저장소 루트에서 실행**한다고 먼저 적고 명시적인 경로를 안내합니다.

```bash
dotnet run --project ./src/HelloReadme/HelloReadme.csproj -c Release
```

프로그램의 실제 출력은 ‘안녕하세요, GitHub!’ 한 줄입니다. 실행 화면 그림에는 학습용 예시라는 표시를 넣었습니다. 화면 파일만 바꾸고 실제 코드나 출력은 예전 상태로 남겨두지 마세요.

### 확인한 것만 적기

필요한 SDK, 명령을 실행할 폴더, 실행 명령, 예상 출력을 적습니다. 다른 사람이 그대로 실행해 결과를 확인할 수 있어야 합니다. 원본 템플릿은 완성 프로젝트가 아니라 골격이므로 자신의 csproj 경로를 만든 후 실행 안내를 갱신하세요.

## 07. GitHub에서 편집하고 검토하기

### 파일 추가와 README 수정은 별도 작업입니다

1. 자신의 작업 브랜치에서 assets·docs·src의 실제 파일을 추가합니다.
2. 루트 README.md를 열고 내용을 수정합니다. GitHub 웹 편집이나 로컬 편집기를 사용할 수 있습니다.
3. 미리보기에서 제목·표·이미지를 확인합니다.
4. 변경 내용 비교에서 오늘 추가한 행과 실행 명령을 확인합니다.
5. 파일을 커밋·푸시하고 PR을 만듭니다. 저장소의 브랜치 규칙을 따릅니다.
6. 실제 PR 주소를 얻으면 README와 pr-log의 해당 기록을 갱신합니다.

템플릿은 main에 직접 작업하기보다 작업 브랜치와 PR을 사용하는 흐름을 안내합니다. PR을 만들기 전에 번호를 추측해서 링크하지 않습니다. 문서가 가리키는 파일도 같은 브랜치에 함께 있어야 합니다.

### 자주 생기는 문제

| 증상 | 먼저 확인할 것 |
| --- | --- |
| 이미지가 깨짐 | 이미지도 커밋했는지, 문서 기준 ../ 개수, 대소문자 |
| 링크를 눌렀는데 없음 | 파일 생성 여부와 같은 브랜치에 있는지 |
| 표가 글자로 보임 | 표 앞 빈 줄, 구분선, 행마다 열 수 |
| 아래 문서까지 코드처럼 보임 | 닫는 백틱 세 개 누락 |
| README가 저장소 첫 화면과 다름 | assets/README가 아니라 루트 README를 수정했는지 |
| 실행 명령이 실패함 | 저장소 루트 기준 csproj 경로와 설치 SDK |

## 08. 완성 예시로 대조하기

### 폴더째 열어서 확인하기

이 폴더의 `samples/완성예시`에는 README·이미지·개발 일지·상세 문서·실제 콘솔 프로젝트를 함께 넣었습니다. HTML 안의 완성 예시는 그 README 원문과 연결됩니다. 소스 파일이나 문서를 추가한 뒤 README 링크를 어떻게 갱신하는지 실제 파일로 비교하세요.

### 직접 하는 과제

프로그램이 자기 이름과 오늘 날짜를 출력하도록 수정하세요. 변경 결과에 맞춰 이미지 또는 새 실행 화면을 assets에 넣고, 자신의 날짜·주제 폴더에 설명을 작성합니다. 개발 일지에 날짜 구역을 추가하고 README 개발 기록 표의 맨 위에 새 행을 넣습니다. 마지막으로 실행 방법이 여전히 맞는지 확인합니다.

완성 예시를 그대로 자신의 오늘 작업인 것처럼 제출하지 않습니다. 파일 경로와 문법은 참고하되 실제 수행한 내용·날짜·PR 링크로 바꿉니다. 기존 템플릿의 자산 폴더 안내 README는 임의로 삭제하지 않고 실제 파일과 함께 관리합니다.
