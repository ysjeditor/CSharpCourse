# 시스템 · 계획 대조: 시스템 계획이 기획서·엔진과 맞는가

> 누가: 시스템 담당
> 언제: 시스템 계획문서 PR을 열기 전 (예: PR #5), 기획서나 엔진 버전이 바뀐 뒤
> 붙여 넣을 것: design/README.md, 엔진 문서(README의 5분 시작 가이드 + docs/engine-guide.md), docs/system-plan.md

## 프롬프트

```text
당신은 게임의 시스템 설계를 검토하는 동료입니다.

[상황]
우리는 세 명(기획 담당·엔진 담당·시스템 담당)이 한 GitHub 저장소에서 C# 콘솔 게임을 만드는 실습을 하고 있습니다.
엔진 담당이 만든 콘솔 엔진을 상속해서 시스템 담당(저)이 게임을 구현합니다.
시스템 계획문서는 기획서의 규칙을 "어느 클래스의 어느 메서드가 무엇으로 지키나"로 옮긴 문서이고,
기획 담당은 이 문서의 "규칙 ↔ 구현 대응표"로 제 PR을 리뷰합니다.

[기획설계문서 시작]
{{기획설계문서}}
[기획설계문서 끝]

[엔진 문서 시작]
{{엔진 문서}}
[엔진 문서 끝]

[시스템 계획문서 시작]
{{시스템 계획문서}}
[시스템 계획문서 끝]

[부탁]
세 문서를 대조해서 아래를 점검해 주세요.
1. 대응표에 빠진 규칙 — 기획서의 기본 규칙 번호와 최종 목표가 대응표에 모두 있는가
2. 숫자 — 계획문서의 상수가 기획서의 숫자와 같은가, 숫자의 출처(규칙 번호)가 적혀 있는가
3. 엔진 이름 — 계획문서가 쓰는 클래스·메서드 이름이 엔진 문서에 실제로 있는가. 없다면 "엔진에 필요한 것"에 적혀 있는가
4. 상태와 흐름 — 계획문서의 상태와 넘어가는 조건이 기획서의 게임 흐름(그림 설명·규칙)과 같은가
5. 다시 시작 — 다시 시작할 때 처음 값으로 돌아가야 하는 데이터가 모두 적혀 있는가
6. 확인 방법 — 대응표의 확인 방법이 사람이 실행해서 해 볼 수 있는 구체적인 행동인가
7. 엔진 문서의 제약(창 크기, 글자, 입력 방식 등)에 걸리는 계획이 있는가

[규칙]
- 계획문서를 고쳐 쓰거나 코드를 대신 써 주지 마세요. 문제를 질문이나 지적으로만 짚어 주세요.
- 지적마다 근거가 된 문장을 어느 문서의 것인지 밝히고 그대로 인용하세요.
- 엔진 문서에 없는 기능을 있다고 가정하지 마세요. 확실하지 않으면 "모르겠다"고 하고, 무엇을 더 알려 주면 되는지 말해 주세요.
- 칭찬과 요약은 빼고, 중요한 것부터 쓰세요.

[답 형식]
번호 목록으로, 항목마다:
- 인용: (문서 이름) "…"
- 점검 번호: (1~7 중)
- 문제: 한두 문장
- 질문: 시스템 담당이 답하거나 다른 담당에게 물어야 할 것 (누구에게 물을지도)
```

## 답을 받은 뒤 사람이 확인할 것

- 엔진 이름에 대한 지적은 엔진 문서와 실제 코드(IntelliSense)에서 직접 확인합니다. AI가 문서를 잘못 읽었을 수 있습니다.
- 엔진에 없는 기능이 필요하면 엔진 담당에게 기능 요청 이슈를 열고, 계획문서 "엔진에 필요한 것"에 번호를 적습니다.
- 기획서의 규칙이 모호해서 생긴 문제는 시스템 담당이 해석해서 정하지 말고 기획 담당에게 묻습니다.
- 계획문서는 시스템 담당이 직접 고치고, PR에서 기획 담당의 리뷰를 받습니다.
