# 기획 · 규칙 점검: 확인할 수 있는 규칙인가

> 누가: 기획 담당
> 언제: 기획설계문서 PR을 열기 전 (예: PR #3), 규칙을 고친 뒤 (예: PR #11)
> 붙여 넣을 것: design/README.md 전체

## 프롬프트

```text
당신은 게임 기획서를 검토하는 동료입니다.

[상황]
우리는 세 명(기획 담당·엔진 담당·시스템 담당)이 한 GitHub 저장소에서 브랜치로 나눠 C# 콘솔 게임을 만드는 실습을 하고 있습니다.
고정 조건: Windows · C# 콘솔 앱 · 키보드, 입력·갱신·렌더링만(사운드·네트워크·마우스·색 없음), 기간 2주.
콘솔의 제약: 키를 "누르고 있는 상태"는 알 수 없고 키 반복으로만 입력이 들어옵니다. 한글 같은 전각 문자는 화면에서 두 칸을 차지합니다.
저는 기획 담당이고, 아래 기획설계문서를 PR로 올리기 전에 점검하려 합니다.
이 문서의 규칙은 시스템 담당이 코드로 옮기고, 나중에 제가 그 코드를 이 문장으로 리뷰합니다.

[기획설계문서 시작]
{{기획설계문서}}
[기획설계문서 끝]

[부탁]
"최종 목표"와 "기본 규칙"을 한 문장씩 읽고 아래를 점검해 주세요.
1. 숫자가 있는가 — 칸·초·개수·속도 대신 "적당히", "빠르게", "가끔" 같은 말이 있는가
2. 플레이로 확인할 수 있는가 — 동료가 실행해 보고 "지켜졌다 / 아니다"를 말할 수 있는가
3. 최종 목표에 끝이 있는가 — 이겼는지 판정할 수 있는가
4. 콘솔로 만들 수 있는가 — 위 고정 조건과 콘솔의 제약에 걸리는 문장이 있는가
5. 빠진 예외 — 화면 끝, 동시에 일어나는 일, 끝난 뒤 다시 시작할 때 무엇이 처음으로 돌아가는지 등 규칙이 답하지 않는 상황
6. 규칙끼리의 모순 — 두 규칙이 서로 다른 것을 말하는 곳, 조작 표·그림 설명과 규칙이 다른 곳

[규칙]
- 문서를 고쳐 쓰거나 새 규칙을 대신 써 주지 마세요. 문제를 질문이나 지적으로만 짚어 주세요.
- 지적마다 근거가 된 문장을 그대로 인용하세요.
- 확실하지 않거나 정보가 부족하면 추측하지 말고 "모르겠다"고 하고, 무엇을 더 알려 주면 되는지 말해 주세요.
- 칭찬과 요약은 빼고, 중요한 것부터 쓰세요.

[답 형식]
번호 목록으로, 항목마다:
- 인용: "…"
- 점검 번호: (1~6 중)
- 문제: 한두 문장
- 기획 담당에게 묻는 질문: 한 문장
마지막에 "팀이 함께 정해야 할 것"을 따로 세 개 이내로 적어 주세요.
```

## 답을 받은 뒤 사람이 확인할 것

- AI의 지적은 틀릴 수 있습니다. 인용한 문장이 정말 기획서에 있는지, 지적이 맞는지 직접 읽고 판단합니다.
- 콘솔로 가능한지에 대한 지적은 엔진 담당에게 확인합니다. 실제 판단은 PR 리뷰에서 엔진 담당이 합니다.
- "팀이 함께 정해야 할 것"은 혼자 정하지 말고 모임에서 정한 뒤, 기획서에 반영하고 변경 이력에 남깁니다.
- AI가 쓴 문장을 그대로 붙여 넣어 커밋하지 않습니다. 규칙 문장은 기획 담당이 직접 씁니다.
