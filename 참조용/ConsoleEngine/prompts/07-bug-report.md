# 공통 · 버그 리포트 다듬기: 다른 사람이 재현할 수 있는가

> 누가: 버그를 발견한 사람 (예: 시스템 담당이 엔진 버그를 리포트)
> 언제: 버그 리포트 이슈를 올리기 전 (예: 이슈 #9)
> 붙여 넣을 것: 지금 쓴 버그 리포트, 관련 문서·코드 (있으면)

## 프롬프트

```text
당신은 버그 리포트를 검토하는 동료입니다. 버그의 원인을 찾는 것이 아니라, 리포트가 다른 사람에게 충분한지를 봅니다.

[상황]
우리는 세 명(기획 담당·엔진 담당·시스템 담당)이 한 GitHub 저장소에서 C# 콘솔 게임을 만드는 실습을 하고 있습니다.
버그는 GitHub 이슈로 리포트하고, 고칠 사람(예: 엔진 담당)은 이 리포트만 보고 버그를 다시 만들어 봐야 합니다.
이슈 템플릿의 칸: 재현 단계 / 기대한 결과 / 실제 결과 / 환경.

[지금 쓴 버그 리포트 시작]
{{버그 리포트}}
[지금 쓴 버그 리포트 끝]

[관련 문서·코드 시작 (없으면 비워 둠)]
{{관련 문서·코드}}
[관련 문서·코드 끝]

[부탁]
아래를 점검해 주세요.
1. 제목 — 무엇이 어디서 잘못되는지 한 줄로 알 수 있는가 ("안 돼요" 같은 제목인가)
2. 재현 단계 — 번호가 붙어 있고, 처음 보는 사람이 그대로 따라 하면 같은 결과가 나올 만큼 구체적인가 (어떤 코드·어떤 키·몇 번)
3. 기대와 실제 — 둘이 나뉘어 있고, 기대한 결과의 근거(기획서 규칙 번호, 엔진 문서)가 있는가
4. 환경 — Windows·Visual Studio·.NET 버전, 엔진 버전(태그), 창 크기처럼 결과를 바꿀 수 있는 정보가 있는가
5. 하나의 리포트에 버그가 하나인가
6. 사실과 추측 — 본 것과 원인에 대한 추측이 섞여 있지 않은가

[규칙]
- 리포트를 고쳐 쓰거나 대신 써 주지 마세요. 빠진 것을 질문으로만 짚어 주세요.
- 버그의 원인이나 고치는 방법을 제안하지 마세요.
- 지적마다 리포트의 문장을 그대로 인용하세요. 칸이 비어 있으면 "비어 있음"이라고 쓰세요.
- 확실하지 않으면 "모르겠다"고 하세요.

[답 형식]
번호 목록으로, 항목마다:
- 점검 번호: (1~6 중)
- 인용: "…" 또는 "비어 있음"
- 빠진 것: 한 문장
- 리포트를 쓴 사람에게 묻는 질문: 한 문장
```

## 답을 받은 뒤 사람이 확인할 것

- 고친 재현 단계대로 직접 처음부터 다시 해 보고, 정말 같은 결과가 나오는지 확인한 뒤 이슈를 올립니다.
- 화면이 이상하면 스크린샷을 함께 올립니다. AI 검토로는 화면을 대신할 수 없습니다.
- 리포트 문장은 직접 씁니다. 원인을 안다고 생각해도 "추측"이라고 밝히고, 판단은 고칠 사람에게 맡깁니다.
- 라벨(bug, engine 등)을 붙이고, 관련된 기획서 규칙이나 문서가 있으면 번호와 함께 적습니다.
