# 시스템 · 테스트 사례: 내 코드가 계획대로 동작하는가

> 누가: 시스템 담당
> 언제: 게임 PR을 열기 전 (예: PR #7, #12, #13), 리뷰에서 변경 요청을 받고 고친 뒤
> 붙여 넣을 것: 기획서의 기본 규칙·최종 목표, 시스템 계획문서의 대응표, 이번 PR의 게임 코드

## 프롬프트

```text
당신은 게임을 손으로 테스트하는 계획을 함께 세우는 동료입니다. 테스트는 제가 직접 실행해서 합니다.

[상황]
우리는 세 명이 C# 콘솔 게임을 만드는 실습을 하고 있습니다. 저는 시스템 담당이고, 엔진을 상속해 게임을 구현했습니다.
게임은 Visual Studio에서 Ctrl+F5로 실행하고 키보드로만 조작합니다.
콘솔의 제약: 키를 "누르고 있는 상태"는 알 수 없고 키 반복으로만 입력이 들어옵니다.
이번 PR이 구현하는 규칙: {{이번 PR이 구현하는 규칙 번호}}

[기획서의 최종 목표와 기본 규칙 시작]
{{기획서 규칙}}
[기획서의 최종 목표와 기본 규칙 끝]

[시스템 계획문서의 대응표 시작]
{{대응표}}
[시스템 계획문서의 대응표 끝]

[게임 코드 시작]
{{게임 코드}}
[게임 코드 끝]

[부탁]
1. 이번 PR이 구현하는 규칙마다 손으로 해 볼 테스트 사례를 만들어 주세요. 정상 경우 하나 이상, 경계 경우 하나 이상
   (예: 화면 끝에서 계속 누르기, 시간이 정확히 목표에 닿는 순간, 끝난 화면에서 다시 시작했을 때 처음 값으로 돌아오는지).
2. 코드에서 규칙과 다르게 동작할 것 같은 줄이 있으면, 고치는 방법이 아니라 "이 줄은 규칙 몇 번의 이런 상황에서 어떻게 되나요?"라는 질문으로 짚어 주세요.
3. 이번 PR 범위 밖의 규칙은 테스트 사례를 만들지 말고, 이번 변경 때문에 깨질 수 있는 것만 "다시 확인할 것"으로 적어 주세요.

[규칙]
- 코드를 고쳐 주거나 새 코드를 써 주지 마세요. 질문과 지적만 해 주세요.
- 코드를 실행할 수 없다는 점을 잊지 마세요. "실행해 보면 이렇게 될 것"이라고 단정하지 말고 "이렇게 될 수 있다"로 쓰세요.
- 지적마다 근거가 된 코드 줄이나 규칙 문장을 그대로 인용하세요.
- 확실하지 않으면 "모르겠다"고 하고, 무엇을 더 알려 주면 되는지 말해 주세요.

[답 형식]
1) 테스트 사례 표: | 규칙 | 준비(어떤 상태에서) | 조작(누를 키와 순서) | 기대 결과(화면에 보여야 할 것) |
2) 코드에 대한 질문: 번호 목록, 항목마다 인용한 줄 + 관련 규칙 번호 + 질문
3) 다시 확인할 것: 짧은 목록
```

## 답을 받은 뒤 사람이 확인할 것

- 테스트 사례를 실제로 Ctrl+F5로 하나씩 해 보고, 기대 결과와 다르면 버그로 다룹니다. AI는 코드를 실행하지 않았습니다.
- 기대 결과가 기획서 문장과 맞는지 다시 읽습니다. AI가 만든 기대 결과가 기획서와 다를 수 있습니다.
- 해 본 사례는 PR 설명의 "확인한 것"에 적습니다. 리뷰하는 기획 담당이 같은 방법으로 확인할 수 있게 됩니다.
- 코드에 대한 질문은 직접 답을 찾고, 고칠 때도 직접 고칩니다.
