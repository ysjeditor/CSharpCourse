# 기획 · 아이디어 시험: 이 규칙을 더하면 어떻게 변하나

> 누가: 기획 담당 (토론 중이면 셋 다)
> 언제: 규칙을 더하거나 바꾸자는 아이디어가 나왔을 때 — 기획서를 고치기 전
> 붙여 넣을 것: 지금의 design/README.md, 더하거나 바꿀 규칙 한두 문장

## 프롬프트

```text
당신은 게임 기획 아이디어를 함께 따져 보는 동료입니다. 결정은 우리 팀이 합니다.

[상황]
우리는 세 명(기획 담당·엔진 담당·시스템 담당)이 C# 콘솔 게임을 만드는 실습을 하고 있습니다.
고정 조건: Windows · C# 콘솔 앱 · 키보드, 입력·갱신·렌더링만(사운드·네트워크·마우스·색 없음), 기간 2주.
콘솔의 제약: 키를 "누르고 있는 상태"는 알 수 없고 키 반복으로만 입력이 들어옵니다. 한글 같은 전각 문자는 두 칸을 차지합니다.

[지금의 기획설계문서 시작]
{{기획설계문서}}
[지금의 기획설계문서 끝]

[시험할 아이디어]
{{더하거나 바꿀 규칙}}

[부탁]
이 아이디어를 기획서에 넣었다고 가정하고, 플레이 장면으로 따져 주세요.
1. 플레이 시나리오 세 개 — 처음 해 보는 사람 / 익숙한 사람 / 규칙의 빈틈을 노리는 사람이 각각 무엇을 하고 어떤 일이 생기는지 시간 순서로
2. 최종 목표에 미치는 영향 — 기획서의 최종 목표(예: 60초 버티기)에 닿기가 쉬워지는지 어려워지는지, 그렇게 보는 이유
3. 새로 생기는 빈칸 — 이 아이디어 때문에 정해야 하는 숫자나 예외 (예: 몇 초마다? 몇 칸? 동시에 일어나면?)
4. 기존 규칙과 부딪히는 곳 — 바꿔야 할 수 있는 규칙 번호와 이유
5. 만드는 사람에게 미치는 영향 — 엔진에 새 기능이 필요할지, 시스템 담당의 일이 얼마나 늘지 (2주 안에 가능한지 판단할 재료)

[규칙]
- 아이디어를 "좋다/나쁘다"로 결론 내리지 마세요. 판단 재료만 주세요.
- 기획서를 고쳐 쓰거나 규칙 문장을 대신 써 주지 마세요.
- 기획서의 문장에 근거할 때는 그 문장을 그대로 인용하세요.
- 확실하지 않으면 "모르겠다"고 하고, 무엇을 더 알려 주면 되는지 말해 주세요.

[답 형식]
위 1~5의 번호를 제목으로 쓰고, 각 항목은 짧은 목록으로.
마지막에 "팀이 정해야 할 질문"을 다섯 개 이내로 적어 주세요.
```

## 답을 받은 뒤 사람이 확인할 것

- AI는 게임을 실제로 해 보지 않았습니다. 시나리오는 상상입니다. 가능하면 종이로 흉내 내거나 지금 게임을 실행해 비슷한 상황을 직접 만들어 봅니다.
- "팀이 정해야 할 질문"은 셋이 모여 정합니다. 결과는 기획서 변경 이력과, 큰 결정이면 결정 기록(ADR)에 남깁니다.
- 엔진·시스템 작업량에 대한 추정은 엔진 담당·시스템 담당에게 직접 묻습니다.
- 넣기로 했다면 기획서를 고치는 PR을 따로 열고, 엔진 담당의 기술 검토를 받습니다.
