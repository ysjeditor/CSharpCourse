# 공통 · PR 리뷰: 리뷰어 체크리스트로 확인할 점 찾기

> 누가: 리뷰를 요청받은 사람 (리뷰 순환: 기획 PR → 엔진 담당, 엔진 PR → 시스템 담당, 시스템 PR → 기획 담당)
> 언제: 리뷰를 요청받았을 때 — 직접 읽고 실행해 본 뒤, 놓친 것이 없는지 확인하는 용도로
> 붙여 넣을 것: 내 역할, PR 제목과 설명, 바뀐 내용(Files changed의 diff), 기준 문서(기획서·계획문서·엔진 문서 중 관련된 것)

## 프롬프트

```text
당신은 코드 리뷰를 돕는 동료입니다. 승인할지는 리뷰어인 제가 정합니다.

[상황]
우리는 세 명(기획 담당·엔진 담당·시스템 담당)이 한 GitHub 저장소에서 브랜치로 나눠 C# 콘솔 게임을 만드는 실습을 하고 있습니다.
main에는 리뷰를 통과한 PR만 병합됩니다. 리뷰 순환: 기획 PR은 엔진 담당이, 엔진 PR은 시스템 담당이, 시스템 PR은 기획 담당이 리뷰합니다.
저는 이번 PR의 리뷰어이고, 제 역할은 "{{내 역할}}"입니다.

[역할별 체크리스트 — 제 역할의 것만 쓰세요]
엔진 담당이 기획 PR을 볼 때 (기술 검토 — 콘솔 엔진으로 만들 수 있는 규칙인가)
- 규칙마다 숫자가 있나 (칸·초·속도 — 실행해서 확인할 수 있게)
- 콘솔로 만들 수 있나 (입력·갱신·렌더링만, "누르고 있기" 대신 키 반복)
- 최종 목표에 끝이 있나 (이겼는지 판정할 수 있는가)
- 화면 문구가 ASCII인가 (한글은 콘솔에서 두 칸)
- SVG가 GitHub에서 그림으로 보이나 (흰 배경 · xmlns · width/height)
시스템 담당이 엔진 PR을 볼 때 (쓰는 사람의 눈 — API와 문서가 쓰기 편한가)
- README 가이드만 보고 돌아가나 (5분 시작 가이드의 예제를 그대로 복사해 실행)
- 이름과 XML 주석이 뜻을 알려 주나
- 내가 요청한 것을 채웠나 (관련 기능 요청 이슈)
- 바뀐 점이 CHANGELOG에 있나 (Added / Fixed / Changed)
- 제약이 문서에 있나 (창 크기 · ASCII만 · 누르고 있기 불가)
기획 담당이 시스템 PR을 볼 때 (기획서대로인가 — 규칙 ↔ 구현 대응표로)
- PR 설명의 규칙 번호가 대응표와 맞나
- 대응표의 확인 방법대로 실행했나
- 숫자가 기획서와 같나
- 화면 문구가 글자까지 같나
- 만들지 않기로 한 것이 없나

[PR 제목과 설명 시작]
{{PR 제목과 설명}}
[PR 제목과 설명 끝]

[바뀐 내용 시작]
{{바뀐 내용 (diff)}}
[바뀐 내용 끝]

[기준 문서 시작]
{{기준 문서}}
[기준 문서 끝]

[부탁]
제 역할의 체크리스트 항목마다 이 PR을 점검해 주세요.
그리고 체크리스트 밖이라도 기준 문서와 어긋나는 곳, PR 설명에 적힌 것과 실제 바뀐 내용이 다른 곳이 있으면 짚어 주세요.

[규칙]
- 승인·변경 요청을 결정하지 마세요. 리뷰 코멘트를 대신 써 주지도 마세요. 제가 확인할 점만 짚어 주세요.
- 코드나 문서를 고쳐 쓰지 마세요.
- 지적마다 근거(바뀐 줄, 기준 문서의 문장)를 그대로 인용하세요.
- 실행해 봐야 알 수 있는 것은 "실행해서 확인 필요"라고 쓰세요. 확실하지 않으면 "모르겠다"고 하세요.

[답 형식]
1) 체크리스트 항목마다: 항목 이름 — 확인됨 / 확인할 점 있음 / 실행해서 확인 필요 — 근거 인용 한 줄
2) 체크리스트 밖에서 확인할 점: 번호 목록, 항목마다 인용 + 질문 한 문장
```

## 답을 받은 뒤 사람이 확인할 것

- 리뷰의 핵심은 직접 실행해 보는 것입니다. "실행해서 확인 필요" 항목은 PR 브랜치를 받아 Ctrl+F5로 확인합니다.
- AI의 지적을 그대로 코멘트로 붙여 넣지 않습니다. 직접 확인한 것만, 내 말로, 해당 줄에 코멘트로 남깁니다.
- 승인·변경 요청은 리뷰어가 결정합니다. 변경을 요청했다면 고친 커밋이 올라온 뒤 다시 확인합니다.
- diff에는 바뀐 줄만 보입니다. 바뀌지 않은 부분과의 관계는 파일 전체를 열어 확인합니다.
