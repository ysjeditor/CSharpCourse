이 교재의 도착점

무엇이 복사되고, 누가 데이터를 계속 사용할 수 있으며, 언제 공간을 회수할 수 있는지 설명할 수 있습니다.

1. SSD에 있던 코드가 화면에 나타나기까지

SSD와 HDD는 전원을 꺼도 파일을 보관하는 저장장치입니다. RAM은 실행 중인 코드와 데이터를 담는 작업 공간입니다. 일반적인 RAM의 내용은 전원이 끊기면 유지되지 않습니다. CPU는 명령을 실행하고 계산합니다.

SSD / HDD
프로그램 파일→RAM
필요한 코드·데이터↔CPU
명령 실행·계산→출력 시스템
화면 갱신
  1. 실행 요청: 운영체제가 프로세스를 준비하고 필요한 실행 파일과 라이브러리를 메모리에 연결합니다. 파일 전체를 한 번에 RAM에 복사해야 하는 것은 아닙니다.
  2. 실행 준비: 일반적인 C# 실행에서는 .NET 런타임이 동작하며, IL이라는 중간 코드를 JIT 컴파일러가 필요한 시점에 CPU용 기계어로 바꿉니다. 미리 기계어로 만드는 AOT 방식도 있습니다.
  3. 계산: 운영체제가 스레드에 CPU 실행 기회를 주면 CPU가 명령을 처리합니다. 데이터는 RAM뿐 아니라 CPU 캐시와 레지스터를 거쳐 사용됩니다.
  4. 출력 요청: 계산 결과로 문자열을 만들거나 UI·그래픽 시스템에 그리기를 요청합니다.
  5. 화면 갱신: 터미널이나 UI 시스템, 운영체제의 화면 합성, 그래픽 장치와 디스플레이 등이 협력해 결과를 표시합니다. 세부 경로는 환경마다 다릅니다.
int hp = 100;
hp -= 20;
Console.WriteLine(hp); // 80이라는 문자를 터미널에 출력하도록 요청

hp -= 20은 데이터를 바꾸는 계산입니다. 이 줄만으로 화면의 체력 표시가 저절로 바뀌지는 않습니다. 화면을 바꾸는 출력 코드나 UI 연결이 필요합니다. 파일에 저장하는 코드가 없다면 SSD의 저장 데이터도 자동으로 바뀌지 않습니다.

RAM이 부족하면 SSD를 RAM처럼 쓰나요?

운영체제는 일부 메모리 페이지를 저장장치로 내보냈다가 필요할 때 다시 가져올 수 있습니다. 이를 페이징과 연결해 이해하면 됩니다. SSD가 RAM으로 바뀌는 것은 아니며, 저장장치 접근이 잦으면 실행이 느려질 수 있습니다.

2. 프로세스는 실행 중인 프로그램의 작업 환경

디스크의 실행 파일은 보관된 프로그램입니다. 그 프로그램을 실행하면 운영체제가 프로세스(process)를 만듭니다. 프로세스에는 주소 공간, 실행에 필요한 자원, 하나 이상의 스레드가 있습니다. 스레드(thread)는 그 안에서 명령을 실행하는 흐름입니다.

프로그램은 보통 가상 주소로 메모리에 접근합니다. 운영체제와 하드웨어가 이 주소를 실제 RAM 등의 저장 공간과 연결합니다. 프로세스마다 독립된 주소 공간이 있어서 같은 숫자의 주소라도 서로 다른 데이터를 가리킬 수 있습니다.

공간주요 역할기억할 점
코드·정적 데이터 등실행할 명령, 정적 수명을 가진 데이터 등스택과 힙 이외의 공간도 있음
스레드 스택메서드 호출과 복귀에 필요한 정보스레드마다 별도의 스택을 가짐
힙개별적으로 할당하고 수명을 관리하는 데이터같은 프로세스의 스레드들이 접근 가능
스택과 힙은 RAM 칩 두 개의 이름이 아닙니다. 프로세스의 메모리를 어떤 규칙으로 사용하고 회수하는지에 따른 구분입니다. 그림의 칸은 개념 모형이며 실제 메모리 배치를 그대로 그린 것은 아닙니다.

3. 호출의 수명과 데이터의 수명이 다르기 때문

스택: 마지막에 시작한 호출이 먼저 끝난다

Main → Play → Damage 순서로 호출하면 보통 Damage → Play → Main 순서로 돌아옵니다. 이 규칙은 접시를 쌓고 위에서부터 꺼내는 것과 같습니다. 호출마다 필요한 정보를 묶은 스택 프레임을 쌓고, 호출이 끝나면 해당 프레임을 되돌릴 수 있습니다.

프레임에는 복귀에 필요한 정보와 일부 인수·지역 변수 등을 둘 수 있습니다. 실제 저장 위치는 최적화에 따라 레지스터 등이 될 수도 있습니다. 프레임이 사라진다는 것은 그 공간을 다시 쓸 수 있다는 뜻이지, 모든 바이트를 즉시 0으로 지운다는 뜻은 아닙니다.

힙: 만든 메서드가 끝나도 남아야 하는 데이터

static Player CreatePlayer()
{
    Player p = new Player();
    p.Hp = 100;
    return p;
}

Player hero = CreatePlayer();
Console.WriteLine(hero.Hp); // 메서드가 끝나도 플레이어는 필요함

class Player { public int Hp; }

CreatePlayer 호출은 끝났지만 호출자에게 전달된 플레이어는 계속 필요합니다. 데이터의 수명이 호출의 수명보다 길어진 것입니다. 이처럼 자유로운 수명을 다루기 위해 힙을 사용합니다.

질문스택힙
어떤 수명에 어울릴까?호출 순서와 함께 끝나는 작업호출과 독립적으로 살아야 하는 데이터
공간 회수 규칙은?호출 복귀에 따라 프레임을 되돌림소유권 규칙이나 GC 등으로 수명을 관리
대가와 제약은?크기가 제한적이며 깊은 재귀로 넘칠 수 있음수명 추적·회수 비용, 단편화 등을 고려

두 영역을 나누는 이유는 단순히 “스택은 빠르고 힙은 느리다”가 아닙니다. 규칙적인 호출에는 간단한 회수 규칙을, 자유로운 수명에는 별도의 관리 규칙을 적용하기 위해서입니다. .NET의 일반적인 작은 객체 할당도 매우 빠를 수 있습니다.

4. 값 타입과 참조 타입: 무엇이 복사될까?

값 타입(value type) 변수에는 그 타입의 값이 들어갑니다. 일반적인 대입은 그 값을 복사합니다. 참조 타입(reference type) 변수에는 객체에 연결되는 참조 값이 들어갑니다. 일반적인 대입은 객체 전체 대신 이 참조 값을 복사합니다.

구분예대입 후의 관계
값 타입int, bool, double, enum, struct복사된 값을 각각 가짐
참조 타입class, 배열, string, delegate같은 객체를 가리킬 수 있음
int a = 10;
int b = a;
b = 20;
Console.WriteLine(a); // 10

Player first = new Player { Hp = 100 };
Player second = first;
second.Hp = 80;
Console.WriteLine(first.Hp); // 80
second = new Player { Hp = 50 };
Console.WriteLine(first.Hp); // 여전히 80

class Player { public int Hp; }

second.Hp = 80은 함께 가리키는 객체를 변경합니다. second = new Player ...는 second의 연결만 바꿉니다. 변수의 참조를 바꾸는 것과 객체의 내용을 바꾸는 것은 다른 행동입니다.

타입과 위치를 한 문장으로 묶지 마세요.

값 타입인 필드도 클래스 객체나 배열의 일부라면 일반적인 모형에서 힙 안에 함께 저장됩니다. 지역 참조 변수는 스택이나 레지스터에 있을 수 있습니다. 타입의 의미를 판단할 때는 위치보다 복사 규칙이 먼저입니다.

Player hero = new Player();
int[] scores = new int[3];
object boxed = 42; // int 값을 박싱한 객체에 복사

class Player
{
    public int Hp = 100; // 값 타입 필드가 Player 객체 안에 포함됨
}

배열 객체에는 값 타입인 int 요소가 포함됩니다. 박싱에서는 값의 복사본을 담는 객체가 생깁니다. new라는 단어만 보고 무조건 힙이라고 판단해서도 안 됩니다. new로 struct를 초기화할 수도 있기 때문입니다.

값 타입 안에 참조 타입 필드가 있으면요?

struct를 복사하면 각 필드의 값이 복사됩니다. 그 필드가 참조라면 참조 값이 복사되므로 두 struct가 같은 객체를 가리킬 수 있습니다. 따라서 값 타입 복사가 내부의 모든 객체까지 새로 만드는 ‘깊은 복사’는 아닙니다.

string은 왜 값을 바꿔도 다른 변수가 안 바뀔까요?
string a = "안녕";
string b = a;
b += "!";
Console.WriteLine(a); // 안녕

string은 참조 타입이지만 불변입니다. 기존 문자열 객체의 내용을 바꾸지 않고, 결과 문자열을 b가 가리키게 합니다. 참조 타입이라는 사실만으로 모든 객체가 수정 가능한 것은 아닙니다.

5. 호출과 객체의 수명을 따라가 보기

아래 버튼으로 호출 흐름을 넘겨 보세요. 객체 이름 A는 학습용 식별자이며 실제 메모리 주소가 아닙니다. 지역 변수는 설명을 위해 스택 칸에 표시합니다.

static Player Create()
{
    Player p = new Player { Hp = 100 };
    return p;
}
Player? hero = Create();
Player? ally = hero;
ally.Hp = 80;
hero = null;
ally = null;
// 이후 적절한 시점에 GC가 실행될 수 있음

class Player { public int Hp; }

Player?는 null을 담을 수 있음을 나타내는 표기입니다. 이 예제는 nullable 참조 타입 검사를 사용하는 프로젝트를 기준으로 합니다.

실행 흐름 모형

호출 / 지역 변수

관리 힙

이 모형은 마지막 단계에서 수집이 일어난 상황을 선택해 보여 줍니다. 실제 JIT는 마지막 사용 이후 변수를 더 일찍 GC 루트에서 제외할 수도 있습니다. 코드의 중괄호 위치나 null 대입만으로 실제 수집 시점을 확정할 수는 없습니다.

6. 참조 타입 전달과 ref는 다릅니다

C#은 기본적으로 인수를 값으로 전달합니다. int라면 정수 값이, Player라면 참조 값이 복사됩니다. 참조 타입을 인수로 넘겼다고 해서 호출자의 변수 자체가 연결되는 것은 아닙니다.

static void Change(Player p)
{
    p.Hp = 80;                   // 같은 객체를 수정
    p = new Player { Hp = 1 };    // 메서드 안의 p만 다른 객체를 가리킴
}

Player hero = new Player { Hp = 100 };
Change(hero);
Console.WriteLine(hero.Hp); // 80

class Player { public int Hp; }

ref를 사용하면 호출자의 변수 저장 위치를 통해 접근할 수 있습니다. 따라서 메서드 안의 재대입으로 호출자의 연결을 바꿀 수 있습니다.

static void Replace(ref Player p)
{
    p = new Player { Hp = 1 };
}
// 위 예제의 hero에 Replace(ref hero)를 호출하면 hero.Hp는 1
직접 예상하기

int 매개변수에 10을 전달하고 메서드 안에서 20을 대입하면 호출자의 변수도 바뀔까요?

기본 전달이면 바뀌지 않습니다. 정수 값의 복사본을 바꾸기 때문입니다. ref를 사용해 호출자의 변수를 변경하는 경우와 구분하세요.

7. 같은 메모리 문제를 다른 규칙으로 다룹니다

스택과 힙은 C#만의 개념이 아닙니다. 언어와 런타임마다 객체의 수명을 결정하고 공간을 회수하는 방법이 다릅니다.

항목일반적인 현대 C++일반적인 C# / .NET
호출과 함께 끝나는 객체자동 저장 기간의 지역 객체는 범위를 벗어나면 소멸자가 실행됨호출 프레임은 복귀하지만 참조 객체의 수집 시점은 별개
동적 객체의 소유권RAII와 unique_ptr 등으로 소유권과 해제를 연결관리 객체는 GC가 도달 가능성을 추적
직접 할당·해제new/delete도 가능하지만 일반 코드에서는 소유권 도구를 우선 사용일반적인 관리 객체에 delete를 호출하지 않음
주요 주의점댕글링 포인터, 이중 해제, 누수 등불필요한 참조 유지, 할당 부담, 수집 일시 정지 등
파일·소켓 등RAII로 객체 소멸 시 자원을 반환IDisposable과 using으로 적절한 시점에 반환

C++: 소유자가 사라질 때 정리하기

#include <memory>
struct Player { int hp = 100; };

int main()
{
    Player local; // 자동 저장 기간의 객체
    auto owner = std::make_unique<Player>(); // 동적 객체의 소유자
} // owner 소멸: 소유한 객체 삭제. local도 소멸.

RAII는 자원의 획득과 반환을 객체의 수명에 묶는 관용구입니다. C++을 “개발자가 모든 메모리를 매번 수동 해제하는 언어”로만 이해하면 현대적인 사용법을 놓칩니다. shared_ptr는 공유 소유권을 참조 횟수로 관리하지만 순환 소유권은 별도 대책이 필요합니다. C++ 표준이 모든 지역 객체의 물리적 스택 배치를 보장하는 것도 아닙니다.

C#: 메모리 회수와 자원 반환을 구분하기

using System.IO;

using (var writer = new StreamWriter("score.txt"))
{
    writer.WriteLine(80);
} // Dispose: 파일 관련 자원을 적절한 시점에 반환
// writer가 가리키던 관리 객체의 메모리는 이후 GC가 회수

using은 GC를 강제 실행하는 문법이 아닙니다. 예외가 나더라도 블록을 벗어날 때 Dispose를 호출하도록 돕습니다. Dispose와 GC는 서로 다른 책임입니다.

8. 정적 타입과 동적 타입은 별개의 축입니다

“정적 언어”라는 표현은 여기서는 정적 타입 언어라는 뜻으로 사용합니다. 이는 static 필드나 정적 메모리 할당을 뜻하지 않습니다.

구분정적 타입: C#, C++동적 타입: Python 등의 일반적인 사용
타입 검사많은 타입 규칙을 실행 전에 검사많은 연산의 타입 적합성을 실행 중 검사
변수 사용선언·추론된 타입에 맞게 사용이름을 다른 타입의 객체에 다시 연결할 수 있음
장점일부 오류를 일찍 발견, 도구의 분석에 유리유연한 표현과 빠른 시도에 유리
기억할 한계컴파일 성공이 모든 오류의 부재를 보장하지 않음객체에 타입이 없는 것은 아님
// C#: var도 정적 타입 추론입니다.
var score = 10;   // score의 타입은 int
// score = "열"; // 컴파일 오류

// dynamic은 해당 연산의 바인딩·검사를 실행 시점으로 미룹니다.
dynamic value = 10;
value = "열";
# Python
score = 10
score = "열"  # 이름 score를 문자열 객체에 다시 연결

타입 검사 시점, 컴파일/JIT/해석 방식, 메모리 회수 방식은 구분해서 보세요. C++과 C#은 모두 정적 타입이지만 대표적인 메모리 관리 방식은 다릅니다. 정적 타입이라고 GC가 없거나, 동적 타입이라고 반드시 같은 GC를 쓰는 것은 아닙니다.

9. GC는 ‘사용할 수 있는 연결’을 따라갑니다

가비지 컬렉터(Garbage Collector)는 .NET 런타임의 메모리 관리 구성 요소입니다. 코드에서 하나 생성하는 청소용 객체라기보다, 관리 힙의 공간을 회수하는 실행 체계로 이해하세요. 핵심 질문은 “이 객체로 다시 도달할 수 있을까?”입니다.

출발점: GC 루트

실행 중인 코드에서 살아 있는 지역 참조·매개변수, 레지스터의 참조, 정적 필드, 일부 런타임 핸들 등이 출발점이 됩니다. 이를 GC 루트(root)라고 부릅니다. GC는 루트에서 시작해 객체의 참조 필드를 따라 연결된 객체를 찾아갑니다.

  1. 도달 가능한 객체 찾기: 루트에서 연결을 따라가며 살아 있는 객체를 표시합니다.
  2. 도달하지 못한 객체 판별: 수집 대상 범위에서 더 이상 도달할 수 없는 객체의 공간을 회수 대상으로 삼습니다.
  3. 공간 회수와 정리: 공간을 재사용할 수 있게 합니다. 압축하는 수집에서는 살아 있는 객체를 옮겨 빈틈을 줄이고 참조도 갱신합니다. 모든 영역이 매번 압축되지는 않습니다.

순환 참조도 수집할 수 있을까요?

루트 → A→A → B → A
서로 참조하는 두 객체

루트에서 A와 B로 도달할 수 있으므로 둘 다 살아 있습니다.

.NET GC는 단순히 참조 개수를 세는 방식이 아닙니다. A와 B가 서로를 참조해도 루트로부터 연결이 끊기면 둘 다 수집 대상이 될 수 있습니다. 반대로 정적 컬렉션이나 이벤트 구독 등이 객체를 계속 붙잡으면, 개발자가 더는 쓸 생각이 없어도 살아남을 수 있습니다.

세대: 오래 사는 객체를 매번 모두 살펴보지 않기

일반적인 작은 객체는 0세대에서 출발합니다. 수집에서 살아남은 객체는 보통 1세대, 이후 2세대로 승격됩니다. 짧게 쓰는 객체가 많다는 경향을 활용해 젊은 세대를 더 자주 수집합니다. 1세대 수집은 0·1세대를, 2세대 수집은 0·1·2세대를 포함합니다.

오래된 객체가 새 객체를 가리키는 연결도 놓치면 안 됩니다. 런타임은 쓰기 장벽(write barrier)과 관련 기록을 이용해 이런 연결이 있는 영역을 추적합니다. 따라서 젊은 세대만 수집할 때도 필요한 참조를 확인할 수 있습니다.

언제 실행되고, 왜 멈칫할까요?

할당량과 메모리 압박 등 런타임의 판단에 따라 수집이 시작될 수 있습니다. GC는 사용자의 “이제 안 쓸게요”라는 의도를 직접 알지 못합니다. x = null은 참조 하나를 끊을 뿐 즉시 수집을 명령하지 않습니다.

수집의 일부 단계에서는 안전하게 참조를 조사하거나 갱신하기 위해 관리 코드 실행을 잠시 멈춥니다. 백그라운드 GC는 작업 일부를 프로그램과 함께 진행하지만 모든 정지를 없애지는 않습니다. 필요 없는 임시 객체를 아주 많이 만들면 할당과 수집 부담이 커질 수 있습니다.

조금 더: 큰 객체와 finalizer

큰 객체는 별도의 대형 객체 힙(LOH)에서 다루며 2세대 수집과 함께 회수됩니다. 이 영역은 일반적으로 매번 압축되지 않습니다. 고정된 객체 등도 이동을 제한할 수 있습니다.

finalizer가 있는 일부 객체는 별도의 마무리 절차 때문에 메모리 회수가 늦어질 수 있습니다. 실행 시점과 순서를 믿고 파일을 닫는 설계를 하지 마세요. 일반적인 자원 반환에는 using/Dispose를 사용합니다.

GC가 해결하는 범위

GC는 도달할 수 없는 관리 객체의 공간을 회수합니다. 불필요하게 유지한 참조의 의도, 파일을 닫아야 하는 시점, 네이티브 메모리의 모든 수명까지 자동으로 해결하지는 않습니다. 일반적인 코드에서 GC.Collect를 반복 호출하는 것을 기본 해결책으로 삼지 마세요.

10. 예상하고, 실행하고, 설명해 보기

먼저 결과를 종이에 적고 콘솔 프로젝트에서 실행해 보세요. 화면 출력만 맞히지 말고, 변수와 객체를 각각 상자로 그린 뒤 연결선을 표시해 봅니다.

using System;

class Player { public int Hp; }
struct Point { public int X; }

class Program
{
    static void Update(Player p, Point point)
    {
        p.Hp = 30;
        point.X = 30;
        p = new Player { Hp = 999 };
    }

    static void Main()
    {
        Player hero = new Player { Hp = 100 };
        Point position = new Point { X = 10 };
        Update(hero, position);
        Console.WriteLine(hero.Hp);
        Console.WriteLine(position.X);
    }
}
출력과 이유 확인
30
10

Player의 참조 값이 복사되어 같은 객체를 수정하므로 Hp는 30입니다. 메서드 안의 p 재대입은 hero의 연결을 바꾸지 않습니다. Point는 값이 복사되어 메서드 안에서 수정한 X가 호출자의 position에 영향을 주지 않습니다.

변형 과제: point 매개변수와 호출부에 ref를 추가하고 결과를 예상하세요. 다음으로 Player 매개변수와 호출부에 ref를 추가해 재대입 결과를 비교하세요.

1. int의 저장 위치에 대한 설명은?

2. hero = null 직후 객체는?

3. using 블록을 벗어나면?

말로 설명할 수 있으면 완료

  • SSD의 파일, 프로세스의 메모리, CPU의 계산, 화면 출력을 구분할 수 있다.
  • 호출이 끝나도 객체가 남아야 하는 예를 들 수 있다.
  • 값 복사, 참조 값 복사, ref 전달의 차이를 설명할 수 있다.
  • GC 루트에서 도달 가능성을 판단하고, 순환 참조의 수집 가능성을 설명할 수 있다.
  • 타입 검사 방식과 메모리 관리 방식을 별개의 기준으로 비교할 수 있다.
