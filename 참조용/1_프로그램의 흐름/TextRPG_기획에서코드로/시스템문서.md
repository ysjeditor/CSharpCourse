# Quest Log — 시스템 설계

## 01. 프로젝트 전체 구조

### 진입점과 책임 분리

기준 프로젝트는 `templates/TextRPG/src/projects/text-rpg`입니다. `Projects/test-rpg`라는 별도 경로는 확인되지 않아 이 통합 프로젝트를 대상으로 문서화했습니다. 정식 프로젝트의 8개 C# 파일에 선언된 **클래스 6개, enum 1개, 최상위 진입 코드**를 분석합니다.

<!-- SVG:architecture -->

`Program.cs`는 `new Game().Run();`으로 시작합니다. 소스에 명시적 Main이 없는 최상위 문 방식입니다. 이전 문서의 명시적 Main으로 바꿀 수 있지만 두 진입 방식을 함께 남기지 않습니다. 파일들은 `TextRpg` 네임스페이스를 사용하며 `Models`, `Systems`는 폴더 구분이지 별도 네임스페이스가 아닙니다.

### 파일을 만드는 순서

`Job → Character·Monster → MonsterCodex·Guild → Battle → Game → Program` 순서로 조립하면 의존하는 형식이 먼저 준비됩니다. 최종 템플릿은 .NET 10, Nullable 분석과 암시적 using을 사용합니다. 파일 범위 namespace는 C# 10 문법이므로 이전 C# 9 호환 문서와 환경이 다릅니다. 이번 실습은 콘솔 .NET 10 프로젝트 기준입니다.

## 02. 모델의 값과 변경 통로

<!-- SVG:models -->

### Character의 계약

이름은 읽기 전용이고 직업·레벨·최대 HP·현재 HP·공격력·처치 수는 클래스 내부에서 변경합니다. 생존 여부는 `Hp > 0`으로 계산합니다. 신규 생성자는 이름과 선택적인 최대 HP·공격력을 받고, 추가 생성자는 기존 길드원 데이터를 받습니다.

| 멤버 | 입력·출력 | 책임 |
| --- | --- | --- |
| `TakeDamage(int amount)` | 반환 없음 | HP를 0 이상으로 유지하며 감소 |
| `Heal()` | 반환 없음 | HP를 MaxHp로 복구 |
| `RollDamage(double critChance = 0.3, double critMultiplier = 1.5)` | `(int damage, bool isCritical)` | 난수 판정과 피해 계산 |
| `RecordKill(int expReward)` | 반환 없음 | 처치 증가와 레벨·스탯 변경 |
| `TryChangeJob(Job wish, out string message)` | bool + 안내 | 조건 검사 후 전직 |
| `SwapHpWith(Character other)` | 반환 없음 | 두 Character의 HP 교환 |
| `Describe()` | string | 현재 상태를 문장으로 표현 |

음수 피해를 받으면 회복처럼 동작할 수 있으므로 TakeDamage가 모든 임의 입력을 검증한다고 해석하지 않습니다. 기본 전투는 양수 공격력을 사용합니다. SwapHpWith도 교환 후 최대 HP로 제한하지 않습니다. 공용 API로 확장할 때 추가할 검증과 현재 동작을 구별하세요.

### Monster와 Job

Monster는 이름·최대 HP·공격력·보상·서식지를 읽기 전용으로 두고 HP만 내부에서 변경합니다. `Clone()`은 원본의 현재 HP가 아니라 **MaxHp**를 사용해 새 객체를 만듭니다. Job은 모험가·기사·도적·마법사의 enum입니다. Character와 Monster 사이의 상속 관계는 없습니다.

## 03. 도감 원본과 전투 사본

<!-- SVG:clone -->

### MonsterCodex가 보유하는 것

고정 데이터는 `Monster[] _monsters`, 처치한 종 이름은 `HashSet<string> _defeated`입니다. `Count`는 배열 길이이고 인덱서 `this[int index]`는 해당 원본 객체를 돌려줍니다. 읽기용 프로퍼티라고 해서 반환한 객체 자체가 불변은 아닙니다.

`Spawn(int index)`는 `Clone()`으로 전투 사본을 반환합니다. UI에서 고른 1~4를 배열 인덱스 0~3으로 바꾸는 것은 Game.Hunt의 책임입니다. Spawn 자체에는 입력 범위 검사가 없습니다.

### 화면 번호를 코드로 바꾸기

1. `int.TryParse`로 숫자 입력을 확인합니다.
2. 1 이상이고 Count 이하인지 확인합니다.
3. `Spawn(pick - 1)`으로 전투 대상을 생성합니다.
4. 승리 후 `MarkDefeated(monster.Name)`로 종의 처치를 기록합니다.

번호를 빼기 전에 검증합니다. 도감 원본을 Battle에 바로 넘기면 전투 피해가 원본에 누적될 수 있습니다. 사본과 원본의 역할을 테스트로 구분하세요.

## 04. 전투 호출과 반환

<!-- SVG:sequence -->

### Battle.Fight는 전투만 처리합니다

`Battle`은 정적 클래스이며 `Fight(Character hero, Monster monster)`가 bool을 반환합니다. 별도 Battle 객체를 생성하지 않습니다. 영웅과 몬스터 객체는 전달받은 참조이므로 HP 변경은 같은 객체에 반영됩니다.

전투는 생존 조건을 검사하면서 영웅 공격 → 몬스터 사망 확인 → 생존 시 반격을 반복합니다. 영웅이 살아남으면 true를 반환합니다. 실제 게임은 살아 있는 새 몬스터와 회복 가능한 영웅을 전달합니다. 임의의 사망 객체를 전달했을 때까지 전투 계약이 검증되어 있는 것은 아닙니다.

### 승패 이후는 Game.Hunt의 책임

승리 후 도감 표시와 RecordKill을 호출하는 것은 Game입니다. 패배 후 Heal도 Game에서 호출합니다. Battle 안에서 보상까지 지급하면 Game의 처리와 중복될 수 있습니다. **호출이 끝나서 돌아오는 자리에서 다음 책임을 연결**하는 연습입니다.

### 치명타의 검증

Character는 정적 Random을 사용합니다. 기본 호출의 피해가 항상 같다고 테스트하지 않습니다. `RollDamage(critChance: 0)`은 일반 피해, `RollDamage(critChance: 1)`은 치명타로 확인할 수 있습니다. 통합 전투에서는 한 방에 처치 가능한 공격력의 테스트 캐릭터를 사용하면 ‘처치 후 반격 없음’을 결정적으로 확인할 수 있습니다.

## 05. 성장·전직을 코드로 번역하기

<!-- SVG:translation -->

### 규칙 문장을 작은 연산으로 나누기

‘큰 보상의 몬스터 또는 짝수 번째 처치에서 성장’은 처치 수를 먼저 증가시킨 후 `expReward >= 30 || Kills % 2 == 0`을 검사합니다. `if` 한 번이므로 동시 충족해도 레벨은 한 번 증가합니다. Exp라는 누적 필드를 새로 만들면 현재 프로젝트와 다른 성장 시스템이 됩니다.

### TryChangeJob의 처리 순서

1. 현재 직업이 모험가인지 확인합니다.
2. 공통 레벨 3 이상인지 확인합니다.
3. switch 식으로 희망 직업별 조건을 검사합니다.
4. 실패하면 안내를 채우고 false를 반환합니다.
5. 성공하면 직업·최대 HP·공격력·HP를 변경하고 true를 반환합니다.

실패 검사가 끝나기 전에 보너스를 적용하지 않습니다. 모든 반환 경로에서 `out message`에 값을 넣어야 합니다. 직업 선택 입력을 Job?로 바꾸고 잘못된 선택을 걸러내는 책임은 Game.ChangeJob에 있습니다.

## 06. 길드의 두 자료구조와 가입 경계

<!-- SVG:storage -->

### 순서와 이름 검색을 함께 만족하기

`List<Character> _members`는 순서 있는 명단을, `Dictionary<string, Character> _byName`은 이름 검색을 담당합니다. 두 곳에 같은 Character 참조를 넣습니다. 값의 복제본을 각각 만들어 넣지 않습니다.

| 메서드 | 실제 책임 | 호출할 때 주의할 점 |
| --- | --- | --- |
| `CanJoin(Character c, out string reason)` | 레벨·처치 조건 계산 | 등록하지 않음. 중복 확인도 하지 않음 |
| `Join(Character c)` | 이름 중복 방지 후 두 구조 등록 | 가입 조건을 내부에서 검사하지 않음 |
| `Find(string name)` | 이름 검색 후 Character? 반환 | 없으면 null |
| `Expel(string name)` | 찾은 객체와 키를 두 구조에서 제거 | 없으면 false |
| `PrintRoster()` | 등록 순서로 Describe 출력 | 빈 명단 안내 포함 |

### 가입 기능 전체의 책임은 호출 순서에 있습니다

플레이어 가입 메뉴는 **Find로 중복 확인 → CanJoin → Join** 순서로 조립합니다. 기존 길드원 시드 등록은 Join을 직접 호출합니다. Join 하나만 연결해두고 가입 자격까지 검사된다고 생각하면 조건 미달 캐릭터가 등록됩니다.

추방은 List만 지우거나 Dictionary만 지우지 않습니다. 삭제 후 Count와 Find를 모두 확인하세요. 조회 결과는 같은 Character이므로 플레이어 성장과 길드 명단의 상태가 연결됩니다.

## 07. Game이 전체 흐름을 조립하는 방법

### Game이 보유하는 상태

Game은 도감 하나와 길드 하나를 생성해 필드로 보관하고, StartScreen 결과를 `_hero`에 저장합니다. 사냥할 때마다 Game·Guild를 새로 만들면 기존 플레이 상태가 사라지므로 수명을 구분해야 합니다.

`Run()`은 시작 화면 → 기존 길드원 등록 → 메뉴 반복 → 종료 메시지 순서입니다. 메인 메뉴에서 문자열을 Trim한 뒤 switch로 기능을 선택합니다. EOF이면 반복을 종료합니다.

### 메서드 분담

| Game 메서드 | 호출하는 협력자 | 처리하는 사용자 흐름 |
| --- | --- | --- |
| `StartScreen()` | Character 생성자 | 이름 정리와 캐릭터 생성 |
| `SeedGuild()` | Guild.Join | 세라·도윤 초기 등록 |
| `Hunt()` | Codex, Battle, Character | 입력 검증과 전투 후 처리 |
| `ChangeJob()` | Character.TryChangeJob | 선택 변환과 성공·실패 표시 |
| `JoinGuild()` | Guild.Find, CanJoin, Join | 중복·자격 확인 후 가입 |
| `ManageGuild()` | Guild.PrintRoster, Find, Expel | 한 번의 관리 작업 |
| `PrintMenu()` | 콘솔 | 메뉴 출력 |

`Game`을 모든 규칙을 담는 거대한 클래스로 만들지 않습니다. 화면을 넘기는 순서는 Game, 캐릭터 변경 규칙은 Character, 명단 일관성은 Guild가 맡습니다.

## 08. 문서에서 파일로 옮기는 실습

### 문장을 코드 요소로 분류하기

| 기획 표현 | 코드 요소 | 실제 예 |
| --- | --- | --- |
| 기억할 숫자·문자 | 필드·프로퍼티 | Hp, Level, Name |
| 정해진 선택지 | enum | Job |
| 허용 조건 | bool 식 | levelOk && killsOk |
| 입력받아 결과 만들기 | 메서드 | RollDamage, TryChangeJob |
| 여러 고정 항목 | 배열 | Monster[] |
| 늘고 줄어드는 명단 | List | _members |
| 이름으로 조회 | Dictionary | _byName |
| 중복 없는 처치 기록 | HashSet | _defeated |
| 계속할 작업과 종료 조건 | while와 switch | Run, Fight |

### 구현 순서와 확인

먼저 빈 콘솔 프로젝트에 8개 파일 경로를 만듭니다. 데이터 생성과 Describe부터 실행해본 뒤 HP 변경, 도감, 길드, 전직·성장, 전투를 순서대로 추가합니다. 모든 파일을 한꺼번에 복사하는 대신 **한 단계마다 빌드하고 확인한 사실을 기록**합니다. 세부 과제와 체크리스트는 두 문서 보기 화면에서 선택할 수 있습니다.

최종 템플릿에는 명시적인 인터페이스·리플렉션·비동기 처리 구조가 없습니다. 이번 과제에서는 필요 없는 중간 계층을 추가하기보다 실제 클래스 간 데이터와 반환값 연결을 먼저 완성합니다.

## 09. 실제 코드와 대조하기

### 구현을 마친 후 확인

아래 파일별 원본은 문서 생성 시점의 프로젝트 코드입니다. 먼저 두 문서의 계약으로 구현하고, 막힌 부분이나 책임 배분을 확인할 때 펼쳐봅니다. 전부 복사하여 실행되는 것과 **기획의 어느 문장이 어느 메서드로 바뀌었는지 설명하는 것**을 구분하세요.
