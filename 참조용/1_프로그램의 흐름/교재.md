# 프로그램의 흐름

Visual Studio에서 C# 코드의 바깥 구조와 실제 실행 순서를 구별합니다.

## 01. Visual Studio 화면에서 길 찾기

### 이번 문서의 목표

처음 C# 프로젝트를 열면 출력문 한 줄보다 그 주위를 감싼 `namespace`, `class`, `Main`, 중괄호가 더 눈에 들어옵니다. 어디에 코드를 적어야 할지, 어디부터 실행되는지 모르겠다는 혼란은 자연스럽습니다. 먼저 **코드를 묶는 구조와 실행되는 문장을 나누어 읽는 방법**부터 배웁니다.

- 솔루션 탐색기에서 `Program.cs`를 찾고 코드 편집기와 실행 결과 창을 구분합니다.
- 각 중괄호가 어느 선언에 속하는지 설명합니다.
- `Main` 안의 순차 실행과 다른 메서드의 호출·복귀를 따라갑니다.
- 실행문을 잘못된 위치에 적었을 때 어디로 옮겨야 하는지 판단합니다.

### Visual Studio의 세 공간

| 공간 | 확인할 것 | 혼동하기 쉬운 점 |
| --- | --- | --- |
| 솔루션 탐색기 | 프로젝트와 `Program.cs` 파일 | 파일을 선택하는 것과 실행하는 것은 다름 |
| 코드 편집기 | 소스 코드와 오류 표시 | 위에 보이는 모든 줄이 위에서부터 실행되는 것은 아님 |
| 콘솔 창 | 프로그램이 출력한 문장과 입력 | Visual Studio의 출력 창과 별도의 프로그램 창일 수 있음 |

아래 패널은 Visual Studio의 역할을 단순화한 **학습용 화면**입니다. 오른쪽에서 구조를 선택하면 해당 범위를 강조합니다. 실제 Visual Studio 화면을 그대로 촬영한 이미지는 아닙니다.

처음에는 패널에서 **Main 본문**을 선택하세요. 우리가 작성할 계산·출력 문장의 기본 위치입니다. 다음에는 클래스, 네임스페이스를 선택하여 Main을 바깥에서 감싸는 구조를 확인합니다. 중괄호의 개수보다 **각 쌍이 누구의 영역을 여닫는지** 말로 설명해보세요.

## 02. 중괄호는 한 덩어리의 시작과 끝

### 여는 괄호와 닫는 괄호

`{`는 영역의 시작이고 `}`는 그 영역의 끝입니다. 여러 영역이 겹칠 수 있으며, 닫는 중괄호는 아직 닫히지 않은 **가장 안쪽 영역**을 먼저 닫습니다. 겉모양은 같아도 네임스페이스·클래스·메서드·조건문 등 무엇을 감쌌는지에 따라 그 안에 적을 수 있는 코드가 달라집니다.

```csharp
using System;

namespace FlowStudy                 // 이름을 묶는 영역
{
    static class Program            // 형식과 멤버를 정의하는 영역
    {
        static void Main()          // 프로그램의 진입 메서드
        {
            Console.WriteLine("안녕하세요"); // 실행할 문장
        }                           // Main 끝
    }                               // Program 끝
}                                   // FlowStudy 끝
```

### 들여쓰기는 소속을 보여줍니다

이 예제에서 출력문은 `Main` 본문에 속하고, `Main`은 `Program` 클래스에 속하며, `Program`은 `FlowStudy` 네임스페이스에 속합니다. 들여쓰기를 단계마다 늘려 읽으면 포함 관계가 드러납니다.

| 포함 관계 | 하는 일 |
| --- | --- |
| `namespace FlowStudy { ... }` | 관련 형식의 이름을 묶음 |
| `static class Program { ... }` | 메서드 등 멤버를 정의 |
| `static void Main() { ... }` | 프로그램 진입점의 처리 정의 |
| `Console.WriteLine(...);` | 실행 중 콘솔에 문장 출력 |

들여쓰기를 지워도 중괄호가 같으면 의미는 유지될 수 있습니다. 반대로 들여쓰기가 예뻐도 중괄호 위치가 다르면 소속은 바뀝니다. **실제 구분 기준은 공백이 아니라 문법과 괄호**입니다.

### 괄호와 세미콜론은 역할이 다릅니다

- `()`는 메서드 선언·호출의 매개변수나 인수를 감쌉니다. 뒤에서 배우는 조건식에도 사용합니다.
- `{}`는 본문이나 묶음의 경계를 표시합니다. 이 예제에서는 선언의 본문입니다.
- `;`는 대입문·호출문 같은 문장을 끝냅니다. 이 예제의 클래스와 메서드 본문 끝에 세미콜론을 추가할 필요는 없습니다.

> 예제의 `{}`는 구조를 설명하기 위한 것입니다. 이후 배열 초기화나 문자열 보간에서도 중괄호가 등장하며, 모든 중괄호가 실행 블록이나 같은 종류의 범위를 만드는 것은 아닙니다.

### 직접 확인하기

출력문 뒤에 있는 닫는 중괄호 세 개를 **Main 끝 → Program 끝 → FlowStudy 끝**이라고 순서대로 읽어보세요. Visual Studio에서 괄호 근처에 커서를 두면 대응하는 괄호 표시를 확인할 수 있습니다. 표시가 헷갈리면 코드 서식 지정 명령으로 들여쓰기부터 정리합니다.

## 03. namespace는 실행 명령이 아닙니다

### 같은 이름을 구별하기 위한 소속

서로 다른 학교에 같은 이름의 학생이 있을 수 있습니다. 학교 이름과 학생 이름을 함께 부르면 구분하기 쉬워집니다. **네임스페이스(namespace)**도 관련 형식의 이름을 묶고 이름 충돌을 줄이는 역할을 합니다.

예제의 클래스 전체 이름은 `FlowStudy.Program`입니다. 여기서 `FlowStudy`는 네임스페이스, `Program`은 클래스 이름입니다. 클래스 이름 `Program` 자체가 실행 시작을 만드는 특별한 명령어는 아닙니다.

### namespace 바깥에서 안으로 ‘실행’되는 것이 아닙니다

이 예제의 실행은 파일 첫 줄에서 네임스페이스를 실행하고, 그다음 클래스를 실행하고, 마지막에 Main을 실행하는 방식이 아닙니다. 빌드 과정에서 선언 구조를 해석하고, 실행 시에는 **선택된 진입점 Main으로 제어가 들어옵니다.**

네임스페이스 안에는 클래스 같은 형식 선언이나 다른 네임스페이스를 배치할 수 있습니다. `Console.WriteLine` 같은 실행문을 네임스페이스 본문에 직접 적을 수는 없습니다. ‘프로그램에 포함되어 있다’와 ‘실행문을 적을 수 있다’는 다른 이야기입니다.

### using System;은 무엇인가요?

이 위치의 `using System;`은 `System` 네임스페이스에 있는 형식을 짧은 이름으로 사용하게 하는 **using 지시문**입니다. `System.Console.WriteLine`을 `Console.WriteLine`으로 쓸 수 있게 합니다. 콘솔을 실행하거나 메서드를 호출하는 문장은 아닙니다.

`using` 지시문을 적었다고 클래스를 생성하는 것도 아닙니다. 또한 뒤에서 배우는 `using` 자원 정리 구문과는 쓰이는 문맥이 다릅니다.

### 실수 점검

| 오해 | 올바른 구분 |
| --- | --- |
| 프로젝트 이름과 namespace는 항상 같아야 한다 | 기본 템플릿이 비슷하게 만들 수 있지만 별도 개념 |
| namespace가 없으면 프로그램이 무조건 실행되지 않는다 | 필수는 아니지만 여기서는 소속 학습을 위해 명시 |
| namespace 안에는 아무 코드나 적는다 | 이 예제에서는 클래스 선언을 배치하고 실행문은 메서드에 둠 |
| using이 위에 있으니 먼저 무언가를 출력한다 | 이름 탐색을 돕는 지시문이며 출력 동작이 아님 |

## 04. Program 클래스와 static을 나누어 읽기

### 클래스는 메서드가 속하는 형식입니다

**클래스(class)**는 데이터와 동작을 정의하는 형식입니다. 이 문서의 `Program` 클래스는 시작 메서드 `Main`과 계산 메서드 `Add`를 담습니다. 클래스 본문에는 메서드·필드·프로퍼티 같은 멤버를 선언합니다.

‘메서드를 클래스 안에 선언한다’와 ‘출력문을 클래스 안에 바로 적는다’는 다릅니다. 전자는 동작을 정의하고, 후자는 메서드 본문에 있어야 할 실행문을 잘못 배치한 것입니다. 필드 초기값처럼 멤버 선언에 식이 들어가는 문법은 뒤에서 별도로 배웁니다.

### static class Program이 뜻하는 것

`static class Program`의 `static`은 **이 클래스의 객체를 new로 만들 수 없고, 객체 생성 없이 정적 멤버를 사용한다**는 뜻입니다. 정적 클래스는 인스턴스 멤버를 가질 수 없으며, 예제에서는 `Main`과 `Add`를 모두 정적 메서드로 선언합니다.

클래스를 static으로 적었다고 프로그램이 시작되는 것은 아닙니다. 클래스 안의 모든 메서드가 자동으로 실행되는 것도 아닙니다. 메서드 실행에는 진입점으로 선택되거나 호출되는 과정이 필요합니다.

### static void Main()이 뜻하는 것

| 부분 | 의미 |
| --- | --- |
| `static` | Program 객체를 만들지 않고 호출할 수 있는 메서드 |
| `void` | 호출한 쪽에 결과값을 반환하지 않음 |
| `Main` | 명시적인 실행 진입점으로 사용할 메서드 이름 |
| `()` | 이 예제에서는 매개변수를 받지 않음 |
| `{ ... }` | 호출되었을 때 수행할 메서드 본문 |

`void`는 출력하지 않는다는 뜻이 아닙니다. 화면에는 출력해도 메서드 결과값을 반환하지 않을 수 있습니다. 뒤의 `Add`는 `int`를 반환하여 이 차이를 보여줍니다.

### 클래스의 static과 Main의 static은 별도입니다

일반적인 템플릿처럼 `class Program` 안에 `static void Main()`을 선언해도 유효합니다. **Program 클래스를 반드시 static으로 적어야 하는 것은 아닙니다.** 이 문서에서는 인스턴스를 만들지 않는 예제를 일관되게 보여주려고 `static class Program`을 사용합니다.

또한 정적 클래스라고 해서 메서드의 `static`을 생략하면 자동으로 정적 메서드가 되지는 않습니다. 정적 클래스 안에 일반적인 인스턴스 메서드를 선언하면 오류가 발생합니다.

## 05. Main에서 시작하는 순차 실행

### 프로그램의 문장 순서

이 문서는 실행 시작 전의 정적 초기화 같은 세부 동작은 잠시 제외하고, **Main에 진입한 뒤 제어가 어떻게 이동하는지**에 집중합니다. Main 본문에서는 기본적으로 위에서 아래로 문장을 실행합니다. 조건문·반복문·메서드 호출을 만나면 그 문법에 맞게 흐름이 바뀝니다.

```csharp
using System;

namespace FlowStudy
{
    static class Program
    {
        static void Main()
        {
            Console.WriteLine("시작");
            int health = 100;
            health = health - 25;
            Console.WriteLine(health);
            Console.WriteLine("끝");
        }
    }
}
```

```text
시작
75
끝
```

### 한 문장씩 추적하기

| 순서 | 실행할 문장 | 처리 후 상태 |
| --- | --- | --- |
| 1 | `Console.WriteLine("시작");` | 콘솔에 시작 출력 |
| 2 | `int health = 100;` | 지역 변수 health의 값은 100 |
| 3 | `health = health - 25;` | 오른쪽을 계산하고 health를 75로 변경 |
| 4 | `Console.WriteLine(health);` | 현재 값 75 출력 |
| 5 | `Console.WriteLine("끝");` | 끝 출력 |
| 6 | Main 본문 끝 도달 | Main이 반환함. 이 단순 콘솔 예제는 종료됨 |

코드가 위쪽에 적혀 있다는 이유로 먼저 호출되는 것은 아닙니다. 같은 클래스 안에서 `Add` 선언을 Main보다 위에 적더라도, 별도로 호출하지 않으면 그 본문은 실행되지 않습니다.

### Visual Studio에서 확인하기

1. 예제를 `Program.cs` 전체에 붙여 넣고 저장합니다.
2. 첫 출력문 왼쪽 여백에 중단점을 설정합니다.
3. 디버깅 시작으로 Main의 첫 출력문에서 멈춥니다.
4. 한 단계씩 코드 실행으로 health가 어떻게 변하는지 확인합니다.
5. 지역 변수 창에서 값을 읽고, 콘솔의 출력 순서와 비교합니다.

일반적인 Visual Studio 기본 키 설정에서 디버깅 시작은 `F5`, 프로시저 단위 실행은 `F10`, 한 단계씩 코드 실행은 `F11`입니다. F10은 메서드 호출을 넘겨 처리하고 F11은 가능한 경우 호출 내부로 들어갑니다. 키 설정이 다르면 **디버그 메뉴의 명령 이름**으로 선택하세요.

> 디버거가 강조하는 줄은 보통 다음에 실행할 문장입니다. `health = health - 25;`에서 멈췄을 때 아직 100으로 보일 수 있으며, 해당 문장을 실행한 뒤 75가 됩니다.

## 06. 메서드 호출은 이동하고 돌아오는 과정

### Main 밖의 메서드는 언제 실행되나요?

Main이 `Add(2, 3)`을 호출하면 제어가 `Add`의 본문으로 이동합니다. 계산 결과를 `return`하면 호출한 자리로 돌아오고, 그 값을 `total`에 저장한 뒤 Main의 다음 문장으로 진행합니다. **호출은 끝이 아니라 복귀 위치를 가진 이동**입니다.

아래 패널의 다음 단계 버튼을 누르며 코드 줄·호출 스택·변수·콘솔 출력을 함께 확인하세요. 정해진 예제를 따라가는 학습용 추적이며, 임의 코드를 컴파일하는 디버거는 아닙니다.

### 지역 변수는 각 메서드의 영역에 속합니다

`left`, `right`, `result`는 Add에서 사용하고 `total`은 Main에서 사용합니다. Main이 `result`라는 이름을 직접 읽는 것이 아니라 **반환한 값**을 `total`로 받습니다. 그림에서 Add가 호출 스택에서 사라진 뒤에도 Main의 total에 5가 남는 이유입니다.

실행이 끝난 뒤 뒤쪽 Add 선언으로 저절로 내려가 다시 실행되는 것도 아닙니다. Main의 마지막 닫는 중괄호는 단순히 다음 선언을 향해 계속 진행하는 줄이 아니라 **그 메서드의 끝**입니다.

### 호출과 선언을 구별하기

| 코드 | 역할 |
| --- | --- |
| `static int Add(int left, int right)` | 입력과 반환형을 가진 메서드 선언 |
| `Add(2, 3)` | 실제 값 2와 3을 전달하는 호출 |
| `return result;` | Add를 끝내고 계산 결과를 호출한 쪽에 반환 |
| `int total = Add(2, 3);` | 반환값을 받아 Main의 지역 변수 초기화 |

`return`은 어디서나 프로그램 전체를 종료하는 문법이 아닙니다. 이 예제에서는 **실행 중인 메서드 Add만 종료**하고 Main으로 돌아옵니다.

## 07. 감싸진 구조 때문에 생기는 실수

### 괄호를 하나 옮기면 코드의 소속이 바뀝니다

| 학생이 겪는 문제 | 흔한 원인 | 확인할 것 |
| --- | --- | --- |
| 출력문에서 문법 오류가 난다 | Main의 닫는 중괄호 뒤, 클래스 본문에 출력문을 작성 | 출력문이 Main의 중괄호 안인지 확인 |
| 클래스가 잘못되었다고 나온다 | 앞의 메서드나 문자열을 닫지 않음 | 오류 위치의 바로 앞 코드도 확인 |
| 변수 이름을 찾을 수 없다 | 다른 메서드의 지역 변수를 직접 사용 | 매개변수·반환값으로 전달할지 판단 |
| 지역 변수를 사용할 수 없다고 나온다 | 같은 메서드라도 더 안쪽 블록에서 선언 | 선언과 사용의 중괄호 범위를 비교 |
| 시작 메서드를 찾을 수 없다 | `main` 오타 또는 유효한 진입점 누락 | 대문자 Main과 static 등 선언 확인 |
| Main을 두 번 정의했다고 나온다 | 기존 Main을 남긴 채 완성 예제를 추가 | 파일 전체와 프로젝트의 다른 파일 확인 |
| Add가 실행되지 않는다 | 선언만 작성하고 호출하지 않음 | Main에 실제 호출이 있는지 확인 |
| static 관련 오류가 난다 | 정적 클래스에 인스턴스 메서드 선언 | 클래스와 메서드의 static을 따로 확인 |
| 줄을 정리했는데도 오류가 남는다 | 들여쓰기만 바꾸고 실제 괄호 위치는 유지 | 여는 괄호와 닫는 괄호의 짝 확인 |

### Main 안에도 더 작은 영역이 생깁니다

조건문·반복문·별도 중괄호 블록 안에서 선언한 지역 변수는 그 영역 밖에서 이름을 사용할 수 없습니다. 반대로 바깥의 지역 변수는 허용된 안쪽 영역에서 사용할 수 있습니다. Main 안이라는 이유만으로 모든 지역 변수를 모든 줄에서 읽을 수 있는 것은 아닙니다.

예를 들어 `if` 본문 안에서 `int bonus = 10;`을 선언했다면, if가 끝난 다음의 출력문에서 bonus를 직접 사용할 수 없습니다. 바깥에서도 필요하다면 **필요한 바깥 영역에 변수를 선언하고 모든 실행 경로에서 값이 대입되는지** 확인합니다.

### 오류가 많을 때의 확인 순서

1. 오류 목록에서 코드 위쪽의 오류 하나를 선택합니다.
2. 그 줄과 바로 앞줄의 큰따옴표·괄호·세미콜론을 확인합니다.
3. Main·Program·namespace의 닫는 중괄호를 안쪽부터 찾습니다.
4. 한 부분만 고친 후 다시 빌드합니다.
5. 빌드가 성공하면 같은 입력으로 실행 결과를 확인합니다.

괄호 하나 때문에 뒤의 코드 전체가 다른 영역으로 해석되면 오류가 연쇄적으로 생깁니다. 오류가 열 개라고 원인도 열 개라고 생각할 필요는 없습니다.

## 08. 최신 프로젝트 화면과 교재가 다를 때

### 최상위 문과 명시적 Main

새 콘솔 앱에서 `Console.WriteLine("Hello, World!");`만 보이는 것은 Main이 필요 없어진 것이 아니라 **최상위 문 기능으로 컴파일러가 진입점을 만들어주기 때문**입니다. 초보자가 배우는 시작 방식이 둘 있다는 뜻입니다.

| 프로젝트에서 보이는 형태 | 이 문서를 따라가는 방법 |
| --- | --- |
| 출력문 한 줄만 있는 최상위 문 | Program.cs 전체를 이 문서의 완성 예제로 교체 |
| 이미 class Program과 Main이 있음 | 기존 전체 구조를 확인하고 중복 정의 없이 교체 |
| `namespace FlowStudy;`처럼 세미콜론으로 끝남 | 파일 범위 namespace라는 다른 문법. 이 문서는 중괄호 형식을 사용 |
| 여러 프로젝트가 솔루션에 있음 | 실행할 프로젝트가 시작 프로젝트인지 확인 |

새 프로젝트 생성 화면에 **최상위 문 사용 안 함** 옵션이 있다면 선택해 명시적인 Main 구조로 시작할 수 있습니다. 옵션 표시와 배치는 설치 버전과 템플릿에 따라 다를 수 있습니다. 화면과 관계없이 이 문서의 완성 예제로 파일 전체를 교체하는 방법을 사용할 수 있습니다.

### 한 파일에서 두 방식을 섞지 않기

기존 최상위 출력문을 남겨둔 채 `static void Main()`을 추가하면, 의도한 Main 대신 최상위 코드가 진입점이 되거나 위치에 따라 오류가 생길 수 있습니다. 단순히 ‘Main을 만들었는데 왜 실행되지 않을까’로 보이기 쉬운 문제입니다.

`using System;`처럼 using 지시문은 최상위 실행문과는 다른 문법입니다. 유지해도 되지만, 기존 `Console.WriteLine` 같은 최상위 실행문과 중복된 `Program` 선언은 함께 점검합니다.

### 이번 학습의 약속

이 문서에서는 **전통적인 namespace 중괄호 + 명시적인 Program 클래스 + Main**의 한 형태로 연습합니다. 이 형식에 익숙해진 다음 최상위 문과 파일 범위 네임스페이스를 비교하면, 생략된 구조를 스스로 복원해서 읽을 수 있습니다.

### 힌트와 해설

실행문을 Main 밖으로 옮긴 경우 클래스의 멤버 선언이 필요한 자리에 실행문이 놓여 오류가 발생합니다. 대입할 변수가 없는 문제가 아니라, **그 문장을 적을 수 없는 영역에 적은 문제**입니다. Add의 인수를 바꾸면 매개변수의 초기값과 반환값이 달라지며, namespace와 클래스의 포함 관계는 그대로입니다.
